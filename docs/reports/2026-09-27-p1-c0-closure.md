## Lost-response replay (C0.4-LOST-RESPONSE-REPLAY: NOT_RUN to PASS)

`tests/integration/lost-response-replay.test.mjs` runs each of three operations
against a real stdio server:
- a legacy promote;
- a GenesisRAG17 submit;
- a Tier-4 graph receipt.

For each one, the harness kills the process with SIGKILL once the write is
durable in SQLite and before any response is read. A fresh process then
replays the request. The checks:
- the replay returns the committed result as `idempotent: true`;
- exactly one committed row exists, with no second Stage 13/14 terminal;
- a changed payload under the same key returns `gks_conflict` (GKS-ING-008).

## Defect found and fixed: concurrent writers and SQLITE_BUSY

The multi-process acceptance test for GKS-IDN-005 showed two faults:
1. **Concurrent writes failed.** When several processes wrote to one store, one
   of them could get `database is locked` straight away. Every write
   transaction was DEFERRED: it read first, and when it then tried to write
   after another process had committed, SQLite returned SQLITE_BUSY. The
   `busy_timeout` setting does not apply in that case.
2. **The error code leaked.** The error went out with the raw code
   `SQLITE_BUSY`, which is outside the GKS error vocabulary (GKS-API-005).

Fixes:
- Every write transaction now begins IMMEDIATE (`writeTransaction` in
  `packages/gks-persistence`), so a second writer waits under `busy_timeout`
  instead of failing.
- The migration runner checks each migration again under the write lock, so two
  processes opening the same store together cannot apply one migration twice.
  Five processes opening a fresh store at once each apply every migration
  exactly once. Without the check the test fails 3 of 3 runs.
- `createJsonRpcToolErrorResponse` now sends only `gks_*` codes. Any other code
  goes out as `gks_backend_unavailable`, with its message unchanged.

`tests/contract/c0-acceptance.test.mjs` proves the fix deterministically:
1. another process holds the write lock for one second and commits while GKS
   waits;
2. with DEFERRED transactions this fails 3 of 3 runs;
3. with IMMEDIATE it passes;
4. the test also asserts that the promote really queued (at least 200 ms), so a
   slow runner fails it loudly instead of passing it without testing anything.

The six-process race test catches the old behaviour about 3 runs in 5, so it
backs up that check rather than standing alone.

**Cost:** idempotent replays (`transactPromotion`, receipt replays) now take the
write lock as well, even when they only read the existing row. Writers are
serialized. That is acceptable for the single-writer profile but should be
revisited if throughput becomes a concern.
