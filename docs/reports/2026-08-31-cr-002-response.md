## Ask (a) — register `smartgift://b2b/portfolio/v1`: ACCEPT, with sequencing

CR-002 §3.D.1 asks:

> Register Schema Contract: Register `smartgift://b2b/portfolio/v1` (v1.3.0) with Vector Spaces: `unboxing_sensory` (1024-dim `bge-m3`) and `product_features`.

**Position: ACCEPT.** Schema-contract registration is registry work squarely inside GKS's Tier 3 ownership — it is metadata about a contract, not execution against a vector index.

**The sequencing note.** "Register" and "embed" are two different pieces of work assigned to two different tiers, and CR-002's own architecture diagram (§1, Tier 3 vs. Tier 4) already draws that line — GKS does not need to redraw it, only hold it:

- **GKS's part, in scope now:** register `smartgift://b2b/portfolio/v1` (v1.3.0) as contract metadata — the vector space names (`unboxing_sensory`, `product_features`), their declared dimensionality (1024) and model (`bge-m3`), and the contract version. This is a registry entry, not a running embedding pipeline.
- **Not GKS's part:** actually computing the 1024-dim `bge-m3` vectors for those two spaces is Stage 15 (`DPS-KI-EMBED`), and `docs/TIER-BOUNDARY-17-STAGE.md`'s ownership table assigns Stage 15 to **GenesisBlockDB (Tier 4)**, not GKS. Registering the contract does not pull embedding execution into GKS, and this response should not be read as GKS volunteering to run it.

**Reference implementation to port, not adopt as-is.** A working bge-m3 1024-dim embedding path already exists at `G:\govibe\packages\msp-runtime\src\retrieval\vector.mjs`. Verified read-only: `createVectorClient` defaults to `DEFAULT_MODEL = "bge-m3"` and `DEFAULT_DIM = 1024` (lines 15–16), calls Ollama's `/api/embeddings` HTTP endpoint, validates the returned vector's length against `dim` before accepting it, and wraps every failure mode — connection refusal, timeout, non-200, malformed payload, dimension mismatch — in a circuit breaker that resolves to `{available: false, diagnostic}` rather than throwing (lines 90–175). Whoever builds Stage 15 should treat this as the reference implementation to **port**, the same relationship `docs/TIER-BOUNDARY-17-STAGE.md` already records for Stage 12's bitemporal semantics against `G:\govibe\packages\msp-runtime\src\domain\temporal-engine.mjs` at commit `79f339e` — re-implemented into the owning package with a fixture-based parity test, not imported live across the repository boundary. GKS names the path; GKS does not import it, and does not build Stage 15 as part of accepting this ask.

**What "accept" commits GKS to today:** adding `smartgift://b2b/portfolio/v1` (v1.3.0) and its two named vector spaces to GKS's schema-contract registry. It does not commit GKS to an embedding execution timeline — that timeline is gated on Stage 15 being designed and built, which is itself gated on the GenesisBlockDB write-path decision in `docs/reports/2026-08-31-gbdb-adapter-decision-brief.md`.

## Ask (b) — dispatch compiled `query-ir.v1` directly to Edge Substrate: FLAG AS A BOUNDARY CONFLICT, propose amendment

CR-002 §3.D.2 asks:

> Query IR Routing: Dispatch compiled `query-ir.v1` requests directly to Edge Substrate.

**Position: FLAG AS A BOUNDARY CONFLICT.** As written, this has GKS opening an outbound call to the Edge Substrate (GenesisBlockDB, per CR-002's own Tier 4 in §1). That is forbidden by the standing rule this repository operates under:

> Call direction (do not invert): `Zuri / GoVibe -> MSP -> GKS`. GKS never calls outward to GenesisBlockDB, GoVibe, or MSP — MSP (`D:\msp`) is GKS's sole caller.
> — `CLAUDE.md`

`docs/ADR-GKS-BOUNDARY.md` fixes the same direction from the architecture side — the decision diagram routes GKS only to its own `GksPersistencePort` and the persistence it selects, never outward to a peer system, and its rejected-alternatives list (`Alternatives rejected`, item 3) rejects any direct connection that bypasses MSP's mediation of scope, context, and authority. "Dispatch... directly to Edge Substrate" is exactly the shape that rule exists to forecloses: a Tier 3 system opening a connection toward a Tier 4 system on its own initiative, with no MSP hop in between.

**Why this is not a simple refusal.** CR-002's ask is not arbitrary — it mirrors zuri-ai's own `ADR-042` (`D:\zuri-ai\docs\decisions\ADR-042-DECOUPLED-STANDALONE-KNOWLEDGE-AND-GRAPHRAG-SERVICE.md`), whose D1 diagram draws GKS ("RAG Intelligence & Orchestration Layer") with an arrow labeled `(Typed Query IR: query-ir.v1)` running straight down to GenesisBlockDB. CR-002 §3.D.2 is a literal reading of that diagram. The conflict is real and comes from a genuine mismatch between two governing documents on two sides of the repository boundary, not from a misunderstanding on either side — which is exactly the case for flagging and proposing an amendment rather than a flat accept or a flat refuse.

**The amendment GKS proposes.** Split "compile" from "dispatch":

- **GKS compiles and returns `query-ir.v1`.** The query plan/IR is GKS's product — `ADR-042` D1's own diagram already names GKS as the layer that owns "Query Planner & Adaptive Router" and produces `query-ir.v1`; that half of CR-002's ask requires no boundary change at all, because GKS returning a compiled artifact to its caller is exactly what GKS already does for every other tool response.
- **The dispatch hop is carried by someone other than GKS.** GKS does not open the connection to the Edge Substrate itself. Two lawful transports already exist for that hop, and CR-002 should pick one rather than invent a third that requires an ADR amendment:
  1. **The caller chain carries it.** `query-ir.v1` rides back up through the existing lawful path — GKS returns it to MSP, MSP returns it to the calling application (Zuri / GoVibe / zuri-ai) — and that caller is the one that dispatches the compiled IR to the Edge Substrate/GenesisBlockDB, exactly as it already does for the rest of Tier 1's outbound calls. No new connection is added anywhere; the existing `Zuri / GoVibe -> MSP -> GKS` path simply carries the IR both directions across the same hops it already crosses.
  2. **The Task 5 decision's pull pattern.** `docs/reports/2026-08-31-gbdb-adapter-decision-brief.md` recommends Option 1: GenesisBlockDB pulls decision records from GKS through a new read-only, cursor-based, scope-enveloped registry tool (`gks_graph_decision_export`), the same shape `docs/ADR-GKS-LEDGER-REPORTING.md`'s D2 already decided for `gks_stage_evidence_export`. If the GenesisBlockDB side of this stack adopts that recommendation, a compiled `query-ir.v1` can travel the identical way: GKS persists the compiled IR, GenesisBlockDB pulls it on its own cursor and its own schedule. GKS never has to know GenesisBlockDB is listening, exactly as that brief argues for graph-decision records.

  Both transports keep the same shape this repository has committed to twice already for adjacent problems: **GKS produces, others carry.** This response's position on ask (b) is deliberately kept consistent with that brief's recommendation rather than arguing a third pattern here.

**If neither transport is workable, that is a boundary-ADR decision, not a CR-002 decision.** If zuri-ai's architecture genuinely requires a direct GKS-to-Substrate call — not merely as a convenience, but as a hard requirement neither transport above can satisfy — that is a proposed amendment to `docs/ADR-GKS-BOUNDARY.md` itself, decided there, by the owner named in that ADR's approval gate, before any implementation. CR-002 cannot authorize that change by itself; naming it explicitly here so it is not smuggled in as an implementation detail once "compile" ships and "dispatch" quietly follows.

**What "flag" commits GKS to today:** building the compile half (`query-ir.v1` returned to GKS's caller) is compatible with ask (a)'s registration work and requires no boundary change. The dispatch half is not accepted as written; GKS asks CR-002 to adopt one of the two named transports, or to open the separate boundary-amendment decision explicitly if neither is workable.

## Ask (c) — never mint `gks:` refs outside GKS: ACCEPT, with one finding

CR-002 §4, invariant 3:

> Canonical Identity Authority: Never mint `gks:` prefixed references outside GKS.

**Position: ACCEPT.** This is an invariant GKS already holds internally — canonical `gks:` identity is minted only inside GKS's own canonicalization path, never by a caller. GKS has no objection to this being written down as a cross-repository invariant; it should already be true everywhere.

**Finding: it is not yet true everywhere.** `G:\govibe\packages\govibe-core\src\poc\msp-stub.mjs` mints `gks:` references today, outside GKS. Verified read-only, three mint sites in that one file:

```js
function canonicalAtomRef(candidateRef) {
  return `gks:atom/${sha256(candidateRef).slice(0, 16)}`;
}

function canonicalRelationRef(fromRef, toRef, type) {
  return `gks:relation/${sha256(`${fromRef}|${type}|${toRef}`).slice(0, 16)}`;
}
```
(`msp-stub.mjs` lines 22–27), plus a third mint site inline in `materialize()`:
```js
materialization_ref: `gks:materialization/${sha256(request.idempotency_key).slice(0, 16)}`,
```
(`msp-stub.mjs` line 147).

The file's own header documents it as "a STUB in deployment terms only" standing in for the MSP promotion boundary plus GKS identity assignment (`msp-stub.mjs` lines 1–7) — it lives under `packages/govibe-core/src/poc/`, a POC directory, but nothing in the file or its path fences it as test-only or excludes it from a plain grep for `gks:` minting outside GKS. As written, a cross-repository invariant check ("grep for `gks:` mints outside `D:\gks`") would fail against this file today, which defeats the purpose of writing the invariant down as something checkable.

**The ask back to GoVibe (relayed, not actioned by GKS):** fence `msp-stub.mjs` so it is unambiguously excluded from production `gks:`-minting surface — either move/rename it under a path or file name that a grep-based invariant check can exclude by convention (e.g. a `__test__`/`fixtures` path, or an explicit `.poc-only.mjs` suffix already excluded from that check), or rename its mint output off the `gks:` namespace entirely (e.g. `stub-atom:`/`poc-gks:`) so no string it produces collides with a real canonical GKS reference even by accident during POC runs. GKS is not proposing which of those two GoVibe should pick — only that CR-002's invariant 3, to be worth stating, needs this file to stop being a counterexample to it. This is a finding for GoVibe to act on, not a change GKS is making to `msp-stub.mjs` itself — GKS has no write access to `G:\govibe` and this response does not ask for any.
