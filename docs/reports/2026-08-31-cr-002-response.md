# GKS response to CR-002 (v1.2.0)

**CR version at time of this response:** `1.2.0`, status `proposed`, `updated_at: 2026-08-30T07:35:00+07:00`. Re-read in full immediately before writing this response — no drift found; the three asks below are quoted from the live text, not from an earlier cached reading.
**Responding repository:** GKS (`D:\gks`)

## Ask (a) — register `smartgift://b2b/portfolio/v1`: ACCEPT, with sequencing

CR-002 §3.D.1 asks:

> Register Schema Contract: Register `smartgift://b2b/portfolio/v1` (v1.3.0) with Vector Spaces: `unboxing_sensory` (1024-dim `bge-m3`) and `product_features`.

**Position: ACCEPT.** Schema-contract registration is registry work squarely inside GKS's Tier 3 ownership — it is metadata about a contract, not execution against a vector index.

**The sequencing note, and whose line it is.** "Register" and "embed" are two different pieces of work assigned to two different tiers — but that split is **GKS's own ownership table**, not something CR-002's diagram already concedes. CR-002 §1's own architecture diagram puts the opposite of that split in writing: its Tier 3 box (the GKS box) lists "GraphRAG Engine: Hybrid Dense Vector (bge-m3 1024-dim) + Graph Traversal (query-ir.v1)" as one of GKS's own governed capabilities (CR-002 line 50), i.e. CR-002 currently draws the vector *engine* itself inside Tier 3, not Tier 4. The Tier 3/Tier 4 split this response is about to state is **GKS proposing a line, per its own document** — `docs/TIER-BOUNDARY-17-STAGE.md`'s ownership table, row 15: `DPS-KI-EMBED` → GenesisBlockDB (Tier 4) — not GKS restating a line CR-002 already drew. CR-002 should read this as a correction GKS is asking for, not agreement it already has:

- **GKS's part, in scope now:** register `smartgift://b2b/portfolio/v1` (v1.3.0) as contract metadata — the vector space names (`unboxing_sensory`, `product_features`), their declared dimensionality (1024) and model (`bge-m3`), and the contract version. This is a registry entry, not a running embedding pipeline.
- **Not GKS's part, per `docs/TIER-BOUNDARY-17-STAGE.md`:** actually computing the 1024-dim `bge-m3` vectors for those two spaces is Stage 15 (`DPS-KI-EMBED`), which that file's ownership table assigns to **GenesisBlockDB (Tier 4)**, not GKS. Registering the contract does not pull embedding execution into GKS, and this response should not be read as GKS volunteering to run it — nor as CR-002 having already agreed to that split, since its own diagram currently says otherwise.

**Reference implementation to port, not adopt as-is.** A working bge-m3 1024-dim embedding path already exists at `G:\govibe\packages\msp-runtime\src\retrieval\vector.mjs`. Verified read-only: `createVectorClient` defaults to `DEFAULT_MODEL = "bge-m3"` and `DEFAULT_DIM = 1024` (lines 15–16), calls Ollama's `/api/embeddings` HTTP endpoint, validates the returned vector's length against `dim` before accepting it, and wraps every failure mode — connection refusal, timeout, non-200, malformed payload, dimension mismatch — in a circuit breaker that resolves to `{available: false, diagnostic}` rather than throwing (lines 90–175). Whoever builds Stage 15 should treat this as the reference implementation to **port**, the same relationship `docs/TIER-BOUNDARY-17-STAGE.md` already records for Stage 12's bitemporal semantics against `G:\govibe\packages\msp-runtime\src\domain\temporal-engine.mjs` at commit `79f339e` — re-implemented into the owning package with a fixture-based parity test, not imported live across the repository boundary. GKS names the path; GKS does not import it, and does not build Stage 15 as part of accepting this ask.

**What "accept" commits GKS to today.** There is no existing schema-contract registry to add an entry to — `packages/gks-contracts/src/tool-definitions.mjs` currently defines eight tools (`gks_health`, `gks_knowledge_promote`, `gks_search`, `gks_entity_get`, `gks_relations_get`, `gks_artifact_link`, `gks_review_list`, `gks_review_apply`) and none of them is a schema-contract surface. Accepting ask (a) commits GKS to building a **new** public tool for this — registered through `packages/gks-contracts`' tool registry per `CLAUDE.md`'s hard rule (never wired directly onto `apps/gks-server`), carrying an explicit scope envelope (`catalogVaultId` / `vaultNamespace` are per-workspace values, per CR-002 §3.A's own `Workspace` model extension, not global), and with no reliance on `GKS_DEFAULT_PORTFOLIO_ID` — that variable exists only for legacy API-010 compatibility and this new tool has no legacy callers to be compatible with. It does not commit GKS to an embedding execution timeline — that timeline is gated on Stage 15 being designed and built, which is itself gated on the GenesisBlockDB write-path decision in `docs/reports/2026-08-31-gbdb-adapter-decision-brief.md`.

## Ask (b) — dispatch compiled `query-ir.v1` directly to Edge Substrate: FLAG AS A BOUNDARY CONFLICT, propose amendment

CR-002 §3.D.2 asks:

> Query IR Routing: Dispatch compiled `query-ir.v1` requests directly to Edge Substrate.

**Position: FLAG AS A BOUNDARY CONFLICT.** As written, this has GKS opening an outbound call to "Edge Substrate." That is forbidden by the standing rule this repository operates under:

> Call direction (do not invert): `Zuri / GoVibe -> MSP -> GKS`. GKS never calls outward to GenesisBlockDB, GoVibe, or MSP — MSP (`D:\msp`) is GKS's sole caller.
> — `CLAUDE.md`

**"Edge Substrate" is ambiguous in CR-002 as written, and this response is reading it, not assuming it.** CR-002 uses the term two ways that do not obviously name the same thing: §1's Tier 4 box is titled "Local Storage Substrate (GenesisBlockDB Native / SmartGift Vault)," while §3.B describes Tier 1's `zuri-rag-service:8888` as the thing that "route[s] edge knowledge retrieval requests to local GenesisBlockDB substrates" — i.e. the edge gateway sits in front of the Tier 4 substrate rather than being it. §3.D.2 itself never says which one it means. This response reads "Edge Substrate" as Tier 4 GenesisBlockDB, the more literal reading of the Tier 4 box's own title, but asks zuri-ai to confirm in the CR whether §3.D.2 means the Tier 4 GenesisBlockDB substrate directly or the Tier 1 `zuri-rag-service:8888` gateway in front of it. **The boundary conclusion below holds either way**: both are outside GKS's own service boundary, so a direct GKS-initiated call to either one is the same conflict under `CLAUDE.md` and `docs/ADR-GKS-BOUNDARY.md`, and the amendment proposed below resolves it either way without needing that ambiguity settled first.

The precise governing text, cited at the passages that actually speak to an *outbound* call from GKS (not the inbound-call prohibition a looser citation could be mistaken for):

- `docs/ADR-GKS-BOUNDARY.md:91-93`: "GKS persistence is selected and governed inside the `D:\gks` boundary. GenesisBlockDB is not selected implicitly. Any future integration between these separate systems requires its own ADR, adapter contract, and approval." A GKS-initiated dispatch call to GenesisBlockDB is exactly the kind of "future integration" this line already requires its own ADR for — it does not yet have one.
- That same ADR's rejected alternative 2 (lines 110–111): "Rename, copy, or treat GenesisBlockDB as GKS. Rejected because it is a separate repository and product, not the GKS extraction source." GenesisBlockDB is treated as external to GKS's own boundary by design, which is what makes an *undeclared* GKS→GenesisBlockDB call a boundary crossing rather than an internal hop.
- `docs/ADR-GKS-LEDGER-REPORTING.md:42-46`, the outward prohibition stated plainly at ADR level rather than only in `CLAUDE.md`: "`ADR-GKS-BOUNDARY.md` states the same prohibition from the other side: GKS never calls outward to GenesisBlockDB, GoVibe, or MSP, and by extension never calls outward to zuri-ai. Put the two together and neither side may open a connection toward the other today, in either direction, as a standing rule rather than a gap waiting to be filled by whichever side gets there first."

(Note on a citation this response is *not* making: `docs/ADR-GKS-BOUNDARY.md`'s rejected alternative 3 — "Let Zuri or GoVibe call GKS directly... bypasses MSP scope, context, and promotion authority" — is an **inbound** prohibition, about callers reaching GKS, not GKS reaching outward. It does not, by itself, govern CR-002 §3.D.2's outbound-dispatch ask; the three citations above do.)

**Why this is not a simple refusal.** CR-002's ask is not arbitrary — it mirrors zuri-ai's own `ADR-042` (`D:\zuri-ai\docs\decisions\ADR-042-DECOUPLED-STANDALONE-KNOWLEDGE-AND-GRAPHRAG-SERVICE.md`), whose D1 diagram draws GKS ("RAG Intelligence & Orchestration Layer") with an arrow labeled `(Typed Query IR: query-ir.v1)` running straight down to GenesisBlockDB. CR-002 §3.D.2 is a literal reading of that diagram. The conflict is real and comes from a genuine mismatch between two governing documents on two sides of the repository boundary, not from a misunderstanding on either side — which is exactly the case for flagging and proposing an amendment rather than a flat accept or a flat refuse.

**A second, correctly-cited finding in the same diagram.** `ADR-042` D1 also draws "Application / Agent (Zuri-AI, GoVibe, NotiKeeper)" with an arrow straight down to "RAG Intelligence & Orchestration Layer (GKS)" — no MSP hop drawn between them. That *is* the shape `docs/ADR-GKS-BOUNDARY.md`'s rejected alternative 3 prohibits ("Let Zuri or GoVibe call GKS directly... bypasses MSP scope, context, and promotion authority"), correctly cited this time because this is the inbound direction that alternative actually governs. This response does not ask zuri-ai to redraw `ADR-042`'s diagram — it notes that the amendment below (transport 1, the caller chain carrying `query-ir.v1` through MSP) already resolves this apparent conflict too, provided the real call path implementing that diagram routes through MSP as `CLAUDE.md` requires, whatever the diagram itself omits for brevity.

**The amendment GKS proposes.** Split "compile" from "dispatch":

- **GKS compiles and returns `query-ir.v1`.** The query plan/IR is GKS's product — `ADR-042` D1's own diagram already names GKS as the layer that owns "Query Planner & Adaptive Router" and produces `query-ir.v1`; that half of CR-002's ask requires no boundary change at all, because GKS returning a compiled artifact to its caller is exactly what GKS already does for every other tool response.
- **The dispatch hop is carried by someone other than GKS**, and which transport carries it depends on whether the call is interactive or not:
  1. **Interactive dispatch — the caller chain carries it. This is the answer for CR-002 §1's stated goal.** `query-ir.v1` rides back up through the existing lawful path — GKS returns it to MSP, MSP returns it to the calling application (Zuri / GoVibe / zuri-ai) — and that caller dispatches the compiled IR to the substrate itself, exactly as it already does for the rest of Tier 1's outbound calls. No new connection is added anywhere; the existing `Zuri / GoVibe -> MSP -> GKS` path simply carries the IR both directions across the same hops it already crosses. **Honest cost, priced the way the GBDB brief prices its options:** this adds a full extra round trip through MSP on top of whatever the caller's own dispatch to the substrate costs — compile-and-return through two hops, then a separate dispatch hop the caller makes itself — against a stated goal of "sub-millisecond latency" (CR-002 §1). That cost is real and this response is not hiding it; it is priced against the alternative of a boundary-breaking direct call, which is not on offer at any latency.
  2. **Non-interactive / pre-compiled IR only — the Task 5 decision's pull pattern.** `docs/reports/2026-08-31-gbdb-adapter-decision-brief.md` recommends Option 1: GenesisBlockDB pulls decision records from GKS through a new read-only, cursor-based, scope-enveloped registry tool (`gks_graph_decision_export`), the same shape `docs/ADR-GKS-LEDGER-REPORTING.md`'s D2 already decided for `gks_stage_evidence_export`. This transport is explicitly **not** a candidate for live, interactive query routing — a consumer-scheduled batch export cannot carry a request that needs a sub-millisecond answer, by construction, regardless of how short the puller's interval is set. It is the right shape only for `query-ir.v1` instances that are pre-compiled ahead of time and consumed on the substrate's own schedule (e.g. a standing or periodically-refreshed query plan), not for a live user-facing query. Scoped this narrowly, it remains consistent with `docs/reports/2026-08-31-gbdb-adapter-decision-brief.md`'s recommendation without overstating what it can carry.

  Both transports keep the same shape this repository has committed to for adjacent problems: **GKS produces, others carry.** This response's position on ask (b) is deliberately kept consistent with that brief's recommendation rather than arguing a third pattern here, but transport 1 — not transport 2 — is the one CR-002 should build its interactive dispatch path against.

**If neither transport is workable, that is a boundary-ADR decision, not a CR-002 decision.** If zuri-ai's architecture genuinely requires a direct GKS-to-Substrate call — not merely as a convenience, but as a hard requirement transport 1's extra hop cannot meet even after that cost is accepted — that is a proposed amendment to `docs/ADR-GKS-BOUNDARY.md` itself, decided there, by the owner named in that ADR's approval gate, before any implementation. CR-002 cannot authorize that change by itself; naming it explicitly here so it is not adopted implicitly once "compile" ships and "dispatch" quietly follows.

**What "flag" commits GKS to today:** building the compile half (`query-ir.v1` returned to GKS's caller) is compatible with ask (a)'s registration work and requires no boundary change. The dispatch half is not accepted as written; GKS asks CR-002 to build interactive routing on transport 1 (with its round-trip cost stated up front), reserve transport 2 for pre-compiled/non-interactive IR only, and to open the separate boundary-amendment decision explicitly if the sub-millisecond target turns out to require more than transport 1 can deliver.

## Ask (c) — never mint `gks:` refs outside GKS: ACCEPT, with one finding

CR-002 §4, invariant 3:

> Canonical Identity Authority: Never mint `gks:` prefixed references outside GKS.

**Position: ACCEPT.** This is an invariant GKS already holds internally — canonical `gks:` identity is minted only inside GKS's own canonicalization path, never by a caller. GKS has no objection to this being written down as a cross-repository invariant; it should already be true everywhere.

**Finding: it is not yet true everywhere.** `G:\govibe\packages\govibe-core\src\poc\msp-stub.mjs` mints `gks:` references today, outside GKS. Verified read-only, three mint sites in that one file:

```js
function canonicalAtomRef(candidateRef) {
  return `gks:atom/${sha256(candidateRef).slice(0, 16)}`;
}

function canonicalRelationRef(fromRef, toRef, type) {
  return `gks:relation/${sha256(`${fromRef}|${type}|${toRef}`).slice(0, 16)}`;
}
```
(`msp-stub.mjs` lines 22–27), plus a third mint site inline in `materialize()`:
```js
materialization_ref: `gks:materialization/${sha256(request.idempotency_key).slice(0, 16)}`,
```
(`msp-stub.mjs` line 147).

The file's own header documents it as "a STUB in deployment terms only" standing in for the MSP promotion boundary plus GKS identity assignment (`msp-stub.mjs` lines 1–7) — it lives under `packages/govibe-core/src/poc/`, a POC directory, but nothing in the file or its path fences it as test-only or excludes it from a plain grep for `gks:` minting outside GKS. As written, a cross-repository invariant check ("grep for `gks:` mints outside `D:\gks`") would fail against this file today, which defeats the purpose of writing the invariant down as something checkable.

**Mitigating fact, checked before writing this finding:** a grep across `G:\govibe` for `msp-stub` finds exactly one importer — the colocated `packages/govibe-core/src/poc/canonical-loop.test.mjs`. Nothing else in GoVibe imports this module. So the risk this finding names is real by *convention* (a grep-based invariant check has no way to know that) but not, today, real by *usage* — the file is already test-only in practice, just not in a way a mechanical check can see. This lowers the urgency of the ask without removing it: GoVibe isn't currently minting stray `gks:` refs into anything that reads them as production identity, but the file remains a live counterexample to invariant 3 the moment anything else imports it, or the moment someone runs a grep-based check that has no usage information to fall back on.

**The ask back to GoVibe (relayed, not actioned by GKS):** fence `msp-stub.mjs` so it is unambiguously excluded from production `gks:`-minting surface — either move/rename it under a path or file name that a grep-based invariant check can exclude by convention (e.g. a `__test__`/`fixtures` path, or an explicit `.poc-only.mjs` suffix already excluded from that check), or rename its mint output off the `gks:` namespace entirely (e.g. `stub-atom:`, which contains no `gks:` substring and so cannot defeat a grep for it) so no string it produces collides with a real canonical GKS reference even by accident during POC runs. GKS is not proposing which of those two GoVibe should pick — only that CR-002's invariant 3, to be worth stating, needs this file to stop being a counterexample to it, and that any renamed prefix actually drop the `gks:` substring rather than merely prefix or suffix it. This is a finding for GoVibe to act on, not a change GKS is making to `msp-stub.mjs` itself — GKS has no write access to `G:\govibe` and this response does not ask for any.
